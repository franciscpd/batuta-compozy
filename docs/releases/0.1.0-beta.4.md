# Batuta v0.1.0-beta.4

`v0.1.0-beta.4` adds a gated publication path and a delivery worktree to
Batuta, from `batuta-ai/compozy`.

## Install

```bash
compozy extension install github:batuta-ai/compozy --allow-unverified --yes
compozy extension enable batuta
```

Pin this version with `github:batuta-ai/compozy@v0.1.0-beta.4`.
Update an existing installation with
`compozy extension update batuta --allow-unverified --yes`; remove it with
`compozy extension remove batuta --global`. The release carries exactly two
assets, `batuta-v0.1.0-beta.4.tar.gz` and
`batuta-v0.1.0-beta.4.tar.gz.sha256`. The daemon verifies the archive against
the sidecar. Manual verification: [docs/verify.md](https://github.com/batuta-ai/compozy/blob/v0.1.0-beta.4/docs/verify.md).

## Breaking change

Direct `batuta-deliver` submissions (cli/http/uds/native_tool/schedule
starts that bypass Batuta's own dispatch) now require a `worktree_ref`
input: `batuta-deliver` runs the whole delivery cycle — `implement-tasks`,
`review-and-fix`, and publication — inside a delivery worktree, and the Loop
can no longer resolve one on its own. Batuta itself creates or reuses that
worktree (`batuta-<slug>`, branch `batuta/<slug>`) before every dispatch it
performs, so this only affects submissions that skip Batuta.

## What's new

- **Delivery worktree isolation.** Every delivery now runs on its own
  managed worktree and branch (`batuta-<slug>` / `batuta/<slug>`), created
  or reused by Batuta with the native worktree tools before the dry-run.
  `implement-tasks` and `review-and-fix` commit inside that worktree, never
  on the base branch. The authored `.compozy/tasks/<slug>` task files reach
  a fresh worktree only through the workspace's `worktrees.copy_list`
  bootstrap-copy configuration; Batuta checks that configuration before
  creating the worktree and refuses to dispatch into an artifact-less one,
  reporting the one-time operator remedy
  (`compozy config set worktrees.copy_list '[".compozy/tasks"]' --scope workspace`).
- **Gated publication.** After a clean review, `batuta-deliver` routes to a
  new `batuta-publisher` resource — the extension's fourth — behind a human
  `publish_gate`. The route to that gate is unconditional on every
  delivery, regardless of `auto_commit` or how many commits landed: the
  daemon exposes no way to prove a branch's commit-ahead-of-base reading is
  fresh rather than stale, so nothing skips the gate on that evidence alone.
  Approving the gate lets `batuta-publisher` verify a clean worktree, read
  the exit plan, push the branch, and open a PR — or, when the branch truly
  carries nothing to publish, report that as a successful outcome instead
  of pushing; or report "pushed, PR manual" with a compare URL when no
  forge provider serves the repository. Rejecting the gate ends the run
  `blocked` with the branch and its commits preserved. Batuta itself never
  pushes, publishes, or approves its own runs; time parked on the gate does
  not consume the delivery budget.
- **Delivery wall-clock budget.** Batuta's Bootstrap phase now provisions a
  4-hour wall-clock budget backstop per workspace
  (`compozy__loop_configure` on `batuta-deliver`, verified and re-checked
  at every dispatch) so the daemon's otherwise-unbounded default never
  governs a dispatch that goes through Batuta. A legitimately long delivery
  is redispatched with the budget raised for that one call. This backstop
  is provisioned by Batuta, not by the Loop definition: a direct
  `batuta-deliver` submission outside Batuta's dispatch path remains
  unbounded until a workspace override exists.
- **Preference gate scoped to delivery.** The `auto_commit` preference gate
  now opens before the session's first delivery-path tool call (task
  preflight, worktree creation, dry-run, or dispatch) instead of before
  every tool call — conversational turns and spec-cycle requirement
  authoring no longer require a config read first.
- **Partial-run audit.** On any non-success terminal where the implement
  child may have started, Batuta now audits per-task landing evidence
  (commit evidence under `auto_commit=true`, worktree state under
  `auto_commit=false`) before offering a redispatch, since a redispatch
  re-executes the full task set and may re-apply already-landed tasks.

Local republication (`scripts/republish.sh`) continues to stage the package
files in a guarded temporary staging directory, validate that exact tree,
then reinstall and enable the extension, unchanged from prior releases.

## Verified scope

The package now contains one `batuta` agent, one `batuta-publisher` agent,
one `batuta-routing` skill, and one `batuta-deliver` Loop — four resources.
Batuta remains resource-only orchestration: it classifies, decomposes,
dispatches, and reports, and does not write implementation code. The
manifest floor remains `v0.3.0-beta.13`; the local operational guard
requires `v0.3.0-beta.14` or later.

## Known upstream limitations

These CompozyOS limitations are unchanged: executor sessions are not
visually nested and remain active/idle after normal terminal completion.

## Merge gate — unattended `approve-reads` publication

Whether a Loop goal node can run `batuta-publisher`'s CLI steps unattended
under `permissions: approve-reads` is unproven as of this release: a probe
showed each step required a manual approval, and `deny-all` auto-rejected
every step outright before it ran. The live approve-path smoke
(`tests/e2e/SMOKE.md`, "Gate de publicação") must prove the publish node
completes unattended before this branch merges. If that smoke stalls on
approval prompts, the publication design needs revisiting — not a
permission bump to `approve-all`, which crosses workspaces silently.
